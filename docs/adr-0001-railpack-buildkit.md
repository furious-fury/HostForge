# ADR 0001: Railpack builds through a dedicated BuildKit frontend

**Status:** Accepted for implementation  
**Date:** 2026-07-11

## Context

HostForge is replacing Nixpacks with Railpack while keeping Docker as the local
runtime. The production build path must not be a `railpack build` CLI wrapper:
Railpack's platform guidance recommends generating a build plan and invoking its
BuildKit frontend directly, because the CLI build path is not designed for
high-throughput platform use. The frontend requires a plan generated by
`railpack prepare`, and Railpack recommends using the same frontend version as
the one that generated the plan. [Railpack production guide](https://railpack.com/guides/running-railpack-in-production/)

This ADR chooses the production topology and the contract that a future builder
adapter must implement. It does not change the active Nixpacks pipeline.

## Decision

### Build topology

- Run one dedicated BuildKit daemon on the Linux VPS, managed independently of
  HostForge and reachable only through its local Unix socket. It is a build
  service, not a public endpoint and not a per-deployment container.
- The HostForge server worker is the BuildKit client. It calls `buildctl` (or a
  Go BuildKit client in a later internal implementation) against that local
  daemon. `docker build`, `docker buildx`, and `railpack build` are not the
  production build engine.
- Keep the Docker daemon as the runtime image store. A successful BuildKit build
  exports a single-platform Linux OCI/Docker image to the local Docker daemon
  under the immutable deployment image reference. The runtime then uses the
  existing Docker lifecycle and loopback-only port binding.
- The worker invokes a pinned Railpack **prepare helper** only to analyze the
  checked-out source and emit `railpack-plan.json` plus `railpack-info.json` in
  the deployment worktree. Build execution is through the pinned Railpack
  frontend image, not the Railpack CLI. The helper and frontend are matching
  versions.

Railpack's frontend compiles its plan to BuildKit LLB, and BuildKit supports
frontends and explicit exporters, which makes this topology appropriate for the
local Docker runtime. [Railpack BuildKit architecture](https://railpack.com/architecture/buildkit/)
[BuildKit exporters](https://docs.docker.com/build/exporters/)

### Build invocation and outputs

For a Railpack deployment, the adapter will:

1. Clone a commit into an isolated worktree and validate its context size and
   `.dockerignore` behavior.
2. Run the pinned `railpack prepare` helper with only the approved build-time
   variables, writing plan and info files outside the committed source tree
   where practical.
3. Submit the source context and plan directory to the local BuildKit daemon
   with `gateway.v0` and the pinned `ghcr.io/railwayapp/railpack-frontend` image
   digest as `source`.
4. Export exactly one `linux/amd64` or `linux/arm64` image—matching the host
   architecture—to the Docker daemon with the generated deployment image tag.
5. Persist sanitized build metadata (builder kind, pinned versions/digests,
   detected stack, image reference, cache key, start metadata, duration, and
   outcome) and stream structured, redacted build events to the existing log
   service.

The first implementation should use the documented `type=docker` export and
load it into the local daemon. It must fail the deployment if image import or
post-import inspection fails; it must never run an unverified image ID.

### Dockerfile fallback

- The default builder selection is Railpack.
- If Railpack planning reports that the repository is unsupported or cannot
  produce a usable deploy plan, and the configured repository root contains a
  regular `Dockerfile`, select the Dockerfile builder as a fallback.
- A future UI/API field may explicitly select Dockerfile, but implicit fallback
  must be recorded in deployment metadata and prominently emitted to the build
  log. A Dockerfile is not silently preferred merely because one happens to be
  present.
- The Dockerfile builder uses the same dedicated BuildKit daemon, explicit
  single-platform output, log/event contract, cancellation, and image-import
  verification as Railpack.
- If neither Railpack nor an eligible Dockerfile can build the source, fail with
  a stable `builder_unsupported` error before a container is started.

### Version and supply-chain policy

- Pin the Railpack prepare helper to a specific release and pin the matching
  frontend image by immutable digest. The initial implementation candidate is
  Railpack `v0.23.0`; implementation must resolve and commit the exact frontend
  digest for the selected CPU architecture before enabling it.
- Do not use `latest` in production configuration. Build metadata records the
  helper version and frontend digest that built every image.
- Upgrade only by changing both pins together, exercising a maintained fixture
  matrix and Dockerfile-fallback tests, and retaining the previous pins until
  an operator-approved rollback window ends.
- Pull frontend and base images through an allowlisted registry path. A failed
  pull, digest mismatch, or unavailable helper fails closed.

### Cache, concurrency, cancellation, and cleanup

- Generate a cache key from the HostForge project ID, builder kind, pinned
  builder version, and target architecture. It isolates cache mounts between
  projects while retaining cache reuse across deployments of the same project.
  Railpack exposes a `cache-key` specifically to prefix mount-cache IDs.
- Start with a global build concurrency limit of one and make it configurable
  only through operator configuration. Queue excess work; do not allow HTTP
  handlers or webhooks to create unbounded concurrent builds.
- Tie the BuildKit solve context to the deployment cancellation context. A
  cancellation or timeout marks the deployment cancelled/failed, terminates the
  active solve, and skips image import and container creation.
- Enforce preflight free-space thresholds for the BuildKit state directory,
  Docker image store, worktree volume, and log volume. Reject a queued build
  below the threshold with a stable low-disk error.
- On terminal state, remove temporary plan/info files and worktrees. Retain
  bounded successful images and their active/rollback candidates; prune only
  images and cache records that are not referenced by a retained deployment.
  Cache eviction must be capacity/age based and never remove an active solve.

### Secrets and source credentials

- GitHub App installation tokens are clone-only credentials. They are never
  included in the BuildKit context, image labels, build arguments, persisted
  metadata, or logs.
- Build-time secrets, when the environment model supports them, are passed as
  BuildKit secrets by name. Their values are redacted from events and are not
  copied into the final image. The adapter computes a non-reversible aggregate
  secret hash for cache invalidation without persisting the secret values.
- Runtime environment variables continue to be injected only when starting the
  container. They are not automatically build arguments.

Railpack distinguishes build secrets from final-image environment variables and
requires secret values to be passed through BuildKit secret mounts when using
the frontend. [Railpack secrets reference](https://railpack.com/architecture/secrets/)

## Consequences

### Positive

- Railpack's supported production frontend path becomes the build engine while
  Docker remains a simple local runtime.
- Build configuration, logs, cancellation, cache policy, and Dockerfile
  fallback can be expressed through a HostForge builder interface rather than
  a Nixpacks CLI process.
- Pinning makes build provenance and controlled upgrades testable.

### Costs and risks

- The VPS install contract now includes a healthy local BuildKit daemon,
  matching architecture, disk monitoring, and frontend image availability.
- The Railpack prepare helper remains a versioned analysis dependency; it is
  intentionally separated from production image execution, but cannot be
  removed until HostForge owns compatible plan generation.
- Direct BuildKit output/import and cancellation behavior need integration
  tests on a clean Linux VPS before the adapter replaces Nixpacks.

## Required implementation checks

- Builder contract tests: Railpack selected, Dockerfile fallback selected,
  unsupported source fails, image import failure fails, and cancellation never
  starts a container.
- Integration tests: matching helper/frontend pin, loopback-only runtime port,
  cache-key isolation, secret redaction/invalidation, low-disk admission,
  retained-image cleanup, and rollback from the previous image.
- Operator validation: BuildKit is local-only, Docker receives the expected
  tagged image, and no application URL exposes a host port.
